# Architecture Rules

- Restrict provider chat records and quiz answer keys to active staff; profiles and roles are readable only by their owner or an active admin, with provider IDs writable only by trusted server code to prevent fabricated reply windows.
- Never mint shared demo staff sessions or authorize scheduled sends with public API keys; retired demo access fails closed and legacy provider read endpoints require active staff to preserve database access boundaries.
- Keep WhatsApp provider calls in shared server-side helpers so webhook automation and staff actions use the same secured gateway path.
- Treat a learner phone number as unambiguous only when it has at most one active WhatsApp course enrollment awaiting a reply.
- The app runs on TanStack Start; WhatsApp callbacks arrive at the public route `/api/public/whatsapp/webhook`, which only verifies the Lovable signature and persists the inbox, messages and statuses — course progression and AI replies are added on top, not inside the signature check.
- Supabase edge functions remain deployed as the rollback path until they are explicitly moved into server functions.
- Chat History and course-page sends use authenticated TanStack server functions and the shared WhatsApp send helper; approved templates are rechecked against the linked WABA before sending to prevent stale approval or language mismatches.
- Chat History checks the incoming-message reply window before enabling WhatsApp free-form sends and treats server window rejections as an actionable template state, not an application crash; the server remains authoritative.
- Verify WhatsApp callbacks using the linked WhatsApp connection key, never the platform gateway key; require delivery/event headers so retries preserve identity.
- Course-page learner chat reuses useWhatsAppChat and the enrollment's phone so it shares persisted provider IDs, delivery updates and secured sending with Chat History; do not create a second message store or merge WhatsApp messages into AI tutor history.
- Each course stores its own WhatsApp welcome template key, lesson intro and completion message; enrollment resolves the latest APPROVED version of that course's key (with its language) so courses never silently share one template.
- Each course has exactly one delivery channel (`courses.delivery_channel`: whatsapp, telegram or web); WhatsApp enrollment and lessons are refused for non-WhatsApp courses.
- Web learners use `/learn`; staff pages redirect non-staff there. Web course content, quiz questions and progress are served and written only by the learner server functions (`src/lib/learner.functions.ts` → `learner.server.ts`) with the service-role client; never send `correct_answer` to the browser and never let learners write enrollments, attempts or certificates directly. Every web step goes through `apply_web_step`, which locks the enrollment (state_version) and rejects stale steps.
- Course progression rules live once, in the pure engine `src/lib/course-engine.ts` (lesson → Next → question → feedback; Pause/Resume; each module is a day unlocked by the course's pacing). WhatsApp (`whatsapp-progression.server.ts`) and web (`learner.server.ts`) only render its outputs; do not fork the rules per channel. The legacy Supabase edge progression does not know about steps or pacing and is a rollback path only.
- Every WhatsApp course step is committed with its outgoing messages through `apply_whatsapp_step` (state_version check) before sending; delivery resumes from `delivered_count`, so retries never repeat or skip a step. Scheduler work uses keys `scheduler:<kind>:<enrollment>:<version>` in the same outbox.
- The course scheduler (`/api/public/course-scheduler`, every 5 minutes via pg_cron → `private.dispatch_course_scheduler`) authenticates with the Vault secret `microlearn_course_scheduler_secret`, checked by `course_scheduler_secret_matches`; it sends free-form lessons/reminders only inside the 24-hour window and otherwise the course's approved nudge template, rechecked on the WABA each run.
- Staff-built WhatsApp flows (keyword, fallback, course_start, course_complete, broadcast) follow one pure engine, `src/lib/flow-engine.ts`: `validateGraph` is shared by the editor and the server (publish is refused on any error) and `runFlow` returns outputs and actions without I/O. Lesson → question progression stays in `course-engine.ts`; flows only hand over to it (Start course) and never fork its rules.
- Flow graphs are published as immutable `whatsapp_flow_versions`; sessions keep the version they started on. Publishing and activation go through `publish_whatsapp_flow` / `set_whatsapp_flow_active`, which keep `whatsapp_flow_keywords` (one flow per keyword) in sync; partial unique indexes allow one active fallback and one active before/after flow per course. Keywords are normalized and checked in both the engine and SQL (`private.normalize_flow_keywords`): course reply words, STOP/UNSUBSCRIBE/START and the `course:`/`quiz:`/`help:`/`flow:` prefixes are never flow keywords, and triggers keep keyword rows only on active keyword flows. Flows are archived (`archived_at`), not deleted; the fallback switch and cooldown are not flow settings. Ask nodes use fixed validators only (never staff regular expressions on the webhook path).
- Every flow step is committed with its outgoing messages through `apply_flow_step` into the `whatsapp_flow_events` outbox before sending; keys are the provider message ID or `flow:<kind>:<session>:<version>`. A start needs an active flow on its current version (test runs excepted) and supersedes the phone's waiting session; continuing needs an open session at the expected state_version; a replayed event returns `already_applied`. A phone has at most one open flow session; a handoff (`handed_off_at`) keeps flows (not course progression) quiet and refuses starts until staff resolve it or 24 hours pass (`expire_stale_flow_sessions`). RPC errors use SQLSTATE class MF.
- Free-form flow messages are only sent inside the 24-hour window: validation requires an approved template that waits for a reply after delays that may outlast it and at the start of broadcasts, and the runtime rechecks the window and the template on the linked WABA. Opt-out (STOP) applies to broadcasts only.
- Inbound WhatsApp messages that progression cannot place (no/ambiguous enrollment, no lessons) get the help menu (`help:courses`/`help:human`, intercepted before progression) via `src/lib/whatsapp-fallback.server.ts`, claimed per provider message ID by `claim_whatsapp_auto_reply` (per-phone cooldown from `whatsapp_bot_settings` + staff flag on `whatsapp_contacts`; no menu while a chat already needs attention, and staff replies restart the cooldown) and delivered from the `whatsapp_auto_replies` outbox; staff clear the flag only through an authenticated server function or by replying.
